## Résumé exécutif

1. Le cœur économique est **solide côté base** : toutes les écritures passent par des RPC `SECURITY DEFINER` avec `search_path=''` et `auth.uid()`. Aucun accès direct aux tables sensibles. `credit_karas`/`debit_karas` ne sont pas exécutables par les joueurs. Une contrainte `karas_balance >= 0` est en place.
2. **Aucune faille de triche exploitable** démontrée : 15/15 tentatives d'écriture directe refusées. Verrous `FOR UPDATE` présents sur packs, enchères, échanges et succès.
3. Les taux de drop **mesurés** sur 100 000 tirages réels du SQL sont conformes aux taux affichés (écarts < 1,2 σ).
4. Le **risque majeur est opérationnel** : la prod a déjà divergé du dépôt (restauration du 26/09 qui a rouvert toutes les fonctions à `anon`), des migrations ont été appliquées à la main, `master` n'est pas protégée et le seul backup documenté est stocké sur le VPS lui-même.
5. La **performance du client** est le second point faible : polling **chaque seconde** de 4 RPC non mises en cache sur Boosters/Collection, y compris en onglet caché. Il y a aussi un N+1 sur les échanges et des listes non bornées.
6. Dette notable : 22 composants et 21 routes `/design-system/*` de preview/preuve publiés en prod, code minifié sur une ligne, test statistique des drops qui ne teste pas le SQL, `README` obsolète.
7. Manques fonctionnels : pas d'interface admin pour traiter les signalements (RPC orphelines), pas de suppression de compte (bloquée de toute façon par des FK `RESTRICT`), pseudo côté serveur toujours `null`.

## Les 5 priorités absolues

1. **INF-01 / COH-01 — Faire un diff réel prod ↔ dépôt, puis l'automatiser.** Lancer le script du § NON VÉRIFIÉ, le comparer au catalogue obtenu par rejeu, puis ajouter un job (manuel ou planifié) qui échoue en cas d'écart. La dérive a déjà ouvert `credit_karas` à `anon` une fois (`20261002000002_restore_api_grants.sql:1-5`).
2. **INF-02 — Backups automatiques hors VPS** : `pg_dump` quotidien chiffré vers un stockage externe (S3/B2), rétention, et un **test de restauration** mensuel. Aujourd'hui, le seul backup documenté est « conservé hors dépôt sur le VPS » (`docs/block-and-report.md:97`).
3. **PERF-01 — Supprimer le polling à 1 s** de `components/game.tsx:37` : limiter aux onglets visibles, passer à 15–30 s et/ou s'appuyer sur les invalidations déjà en place (`subscribePlayerSnapshotInvalidation`).
4. **INF-03 — Protéger `master` côté serveur.** Si GitHub Pro n'est pas envisageable, utiliser au minimum un ruleset ou passer le dépôt en organisation. Ajouter à la CI un job qui rejoue **toutes** les migrations sur base vierge (QUA-02).
5. **SEC-01 + SEC-03 — Durcir les entrées non validées et les dépendances** : valider `p_avatar_url` dans `update_profile` (origine du bucket `avatars` uniquement), ajouter une CSP, lancer `npm audit fix` (sharp, source-map-js).

## Simulation des drops (mesure réelle sur SQL)

Simulation sur PGlite après rejeu des 89 migrations, catalogue de test à 20 cartes par rareté. **10 000** appels réels à `open_regular_pack()` (50 000 cartes) et 10 000 à `open_decision_pack()` (50 000 choix), joués en rôle `authenticated`. Le timer est remis à zéro entre chaque appel.

**Résultat (exécuté le 08/10/2026, 1 799 s) :**

| Pack                     | Rareté | Attendu         | Observé          | Écart (σ) |
| ------------------------ | ------ | --------------- | ---------------- | --------- |
| Régulier (50 000 cartes) | C      | 72,4 % (36 200) | 72,35 % (36 177) | −0,2      |
|                          | R      | 20 % (10 000)   | 19,90 % (9 951)  | −0,5      |
|                          | SR     | 7 % (3 500)     | 7,14 % (3 568)   | +1,2      |
|                          | SSR    | 0,5 % (250)     | 0,51 % (255)     | +0,3      |
|                          | LR     | 0,1 % (50)      | 0,098 % (49)     | −0,1      |
| Décisif (50 000 choix)   | SR     | 96,5 % (48 250) | 96,46 % (48 232) | −0,4      |
|                          | SSR    | 3 % (1 500)     | 3,04 % (1 520)   | +0,5      |
|                          | LR     | 0,5 % (250)     | 0,50 % (248)     | −0,1      |

**Conclusion : les probabilités appliquées par le SQL sont conformes à celles affichées**, avec tous les écarts sous 1,2 σ.
Shiny : 0 sur 297 LR tirés (0,3 attendu, probabilité de 0 ≈ 74 %). C'est compatible avec 0,1 %, mais l'échantillon est trop
petit pour mesurer ce taux : il reste vérifié par lecture du code (`random() < .001` conditionné à LR).

Observation produit (BIZ-09, Info) : avec Shiny = 0,1 % × LR 0,1 %, un Shiny direct sort en moyenne **1 fois par million
de cartes** du Booster Régulier. Au rythme maximal (1 pack / 10 min, soit 720 cartes/jour), il faut environ 3,8 ans par joueur.
Le commit `fbf3d04` annonçait « LR Shiny 1 % », abaissé à 0,1 % par `20261002000003`.
**Statut BIZ-09 : Accepté (choix produit) — PR #161 — 11/10/2026.** Taux confirmé par le propriétaire du produit ; aucune modification du code ni des probabilités.

Effet de bord mesuré : le temps de simulation croît de façon quadratique (voir PERF-09).

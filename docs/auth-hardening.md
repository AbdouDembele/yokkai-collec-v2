# Durcissement Auth — déploiement manuel

**Prérequis bloquant constaté : la configuration locale de l’origine accepte encore les connexions hors Cloudflare ; sa joignabilité extérieure reste à tester. Tant que ce chemin est possible, aucune des protections fondées sur la confiance des en-têtes IP ne doit être considérée fiable. Fermer les entrées web de l’origine avant toute activation du chemin IP ou de son limiteur. Le captcha et les contrôles de mot de passe ne remplacent pas cette fermeture.**

Cette procédure est un livrable de configuration, pas une application des réglages. La PR A ajoute le parcours e-mail et les modèles ; les PR C (IP) et B (Turnstile) sont indépendantes. Aucun compte existant ne doit être modifié, supprimé ou rétroactivement « vérifié ».

## Référence 1 — DKIM, puis DMARC, puis livraison réelle

1. Identifier l’offre et le domaine expéditeur dans OVH. Activer DKIM selon cette offre ; publier exactement le sélecteur et la clé publique TXT/CNAME fournis par OVH, sans inventer de sélecteur. Les enregistrements mail/DKIM sont DNS only. Vérifier la résolution, puis la signature DKIM alignée dans un e-mail reçu. Retour arrière : restaurer l’enregistrement précédent et le réglage OVH ; tenir compte du TTL.
2. Conserver SPF actuel : TXT à la racine, valeur v=spf1 include:mx.ovh.com -all. Ne pas créer un second SPF ni autoriser des services non utilisés. À revérifier si le fournisseur change.
3. Publier TXT _dmarc : v=DMARC1; p=none; adkim=r; aspf=r; pct=100. Aucun destinataire de rapports n’est inventé : ajouter rua seulement après choix d’une boîte contrôlée et vérification des autorisations nécessaires. Vérifier absence de doublon et résolution. Retour arrière : supprimer le nouveau TXT ou restaurer l’ancien. Ne pas passer à quarantine/reject avant validation des expéditeurs légitimes.
4. Envoyer un e-mail réel borné via le chemin Auth vers une boîte contrôlée ; confirmer réception, DKIM/SPF alignés et dmarc=pass dans les en-têtes du destinataire, pas seulement une acceptation SMTP. Si cela échoue, ne pas activer la confirmation obligatoire. Le test de livraison sera une opération distincte autorisée, pas une rafale.

Ce comportement est à recontrôler lors d’une mise à jour d’Auth. Ne pas essayer d’épuiser les budgets de production pour le prouver.

L’interface distingue le quota global, le délai par adresse et l’indisponibilité de l’envoi. GoTrue réutilise over_email_send_rate_limit pour les deux limites : le message fixe de fréquence est reconnu, sans afficher le texte fournisseur. Les erreurs génériques de base de données restent des erreurs Auth, pas de faux diagnostics SMTP. Une réponse SMTP acceptée ne garantit pas la livraison ; un refus SMTP peut être présenté comme erreur d’envoi, sans son détail technique.

## Référence 5 — PR C, confiance réseau puis limiteur d’IP

Recommandation : Next → Envoy par un réseau Docker privé dédié aux seuls conteneurs Next et Envoy, sans publier de port. Le navigateur garde l’API publique. Repasser par Cloudflare pour chaque Server Action ajoute un trajet et fait voir l’IP de sortie du VPS, pas celle du joueur. Le code conserve l’URL publique pour les cookies et REST, et réécrit les seules requêtes Auth vers SUPABASE_AUTH_INTERNAL_URL si cette URL et AUTH_REAL_IP_ENABLED=true sont définis. L’URL seule, l’indicateur seul ou toute valeur autre que la chaîne exacte true conservent le chemin public. Le nom historique sb-api-auth-token est fixé à partir de l’URL publique dans les trois clients (navigateur, serveur, proxy de renouvellement), conformément à @supabase/ssr 0.12.7.

**Préalable obligatoire, manuel : fermer l’origine et établir la preuve.** Déployer PR C avec AUTH_REAL_IP_ENABLED absent ou false, même si l’URL interne est déjà renseignée. Ajouter un réseau dédié Next/Envoy ; choisir le nom DNS réel d’Envoy (la valeur ci-dessous est une cible à vérifier, pas une découverte du réseau actuel). Sur chaque route Traefik HTTPS du site ET de l’API, appliquer dans cet ordre : IPAllowList sur les plages IPv4 et IPv6 Cloudflare officielles, sans ipStrategy.depth/excludedIPs (contrôle de RemoteAddr, pas de XFF client), puis middleware headers. Ce dernier écrase X-Auth-Proxy-Secret avec le secret partagé et supprime X-Auth-Client-IP et Sb-Forwarded-For du trafic public. Couvrir tous les alias, routes alternatives et ports ; réserver SSH à l’administration. Ne pas remplacer ce contrôle par une liste d’IP prise dans un en-tête. Si un intermédiaire supplémentaire masque le pair Cloudflare, arrêter et définir son authentification ; ne pas choisir arbitrairement un nombre de trusted hops.

Avant la fermeture, sauvegarder les règles Traefik/pare-feu dans le gestionnaire d’exploitation, vérifier l’accès à la console de secours et conserver une session SSH ouverte. Garder une règle SSH réservée à l’administration indépendante de la liste Cloudflare ; vérifier une seconde connexion SSH avant et après le changement. Depuis un réseau mobile, vérifier le site et l’API via leurs domaines publics, puis tester l’origine directement avec les mêmes Host/SNI (par exemple curl --resolve avec l’IP réelle conservée hors dépôt), en IPv4 et IPv6 si disponibles : elle doit refuser même avec CF-Connecting-IP et X-Auth-Client-IP forgés. Aucun appel Auth créant des données n’est nécessaire. Contrôler tous les alias et ports web alternatifs ; le test mobile doit précéder l’activation.

Retour arrière de la fermeture : si le site/API public ou l’accès administratif échoue, ne pas activer le chemin IP ni le limiteur. Depuis la session SSH conservée ou la console de secours, restaurer seulement les règles web sauvegardées, sans modifier la règle SSH ; vérifier une nouvelle connexion SSH et les domaines publics depuis le réseau mobile. Si des protections IP avaient déjà été activées, désactiver d’abord RATE_LIMIT_HEADER puis AUTH_REAL_IP_ENABLED et redémarrer les services concernés, selon l’ordre de retour arrière ci-dessous, avant de rouvrir une entrée web. Une origine rouverte annule la confiance IP ; aucune reprise de l’activation avant correction et nouveau test.

Générer AUTH_PROXY_SECRET aléatoirement (32 octets, 64 caractères hexadécimaux minuscules) dans le gestionnaire sécurisé, jamais dans le dépôt ou ce document. Injecter la même valeur côté Next, middleware Traefik et modèle Envoy ; ne jamais l’ajouter à une réponse HTTP, aux journaux ou à une variable NEXT_PUBLIC. La preuve ne sert pas de clé API Supabase. Elle garantit que CF-Connecting-IP provient du chemin autorisé : sans elle, Next refuse les appels internes. Aucun champ de formulaire ni XFF navigateur ne peut choisir l’IP. Un acteur disposant de cette preuve ou d’un conteneur de confiance appartient au périmètre privilégié ; limiter ses accès. En présence de Workers/relais Cloudflare, vérifier aussi la provenance des en-têtes et les restrictions de zone ; utiliser si nécessaire les certificats d’Authenticated Origin Pulls propres à la zone.

Dans volumes/api/envoy/lds.template.yaml, ajouter ce filtre Lua sur le listener Auth avant les filtres Lua de clés API et router. Le générateur déployé utilise une liste sed explicite qui ne contient pas AUTH_PROXY_SECRET : ajouter une substitution dédiée de ce marqueur, sans modifier les substitutions existantes et après validation du format hexadécimal de 64 caractères. Contrôler le fichier rendu sans afficher le secret. Le marqueur du modèle ne doit jamais rester littéral. Conserver les autres routes, réécritures et validations de clé publique. L’extrait a passé --mode validate avec Envoy 1.39.1 dans un conteneur local sans réseau et une preuve factice ; valider aussi la configuration complète rendue avant tout redémarrage. Il ne s’agit pas d’une modification appliquée :

```yaml
- name: envoy.filters.http.lua
  typed_config:
    "@type": type.googleapis.com/envoy.extensions.filters.http.lua.v3.Lua
    default_source_code:
      inline_string: |
        function envoy_on_request(handle)
          local h = handle:headers()
          local proof = h:get("x-auth-proxy-secret")
          local ip = h:get("x-auth-client-ip") or h:get("cf-connecting-ip")
          h:remove("x-auth-proxy-secret")
          h:remove("sb-forwarded-for")
          if string.sub(h:get(":path") or "", 1, 9) ~= "/auth/v1/" then return end
          if proof ~= "${AUTH_PROXY_SECRET}" or not ip or #ip > 45
             or string.find(ip, "[^0-9a-fA-F:.]") then
            handle:respond({[":status"] = "403"}, "Forbidden")
            return
          end
          h:replace("x-auth-client-ip", ip)
          h:replace("x-forwarded-for", ip)
          h:remove("cf-connecting-ip")
          h:remove("x-real-ip")
        end
```

L’IP publique vient de CF-Connecting-IP après filtrage du pair Cloudflare ; l’IP interne vient de Next, qui utilise isIP et vérifie la preuve. Traefik supprime l’en-tête interne sur le chemin public, donc un navigateur ne peut gagner la priorité. Ne pas rendre Envoy accessible par une autre entrée dépourvue de ces règles. X-Forwarded-For est écrasé avec cette IP unique : GoTrue 2.196.0 utilise autrement sa première IP valide pour les audits et la vérification Turnstile. use_remote_address=true et xff_num_trusted_hops=0 peuvent rester : le pair réseau d’Envoy est Traefik/Next, mais les fonctions Auth reçoivent la valeur canonique. En-têtes dupliqués/combinés sont refusés. L’expression Lua contrôle le format unique ; la validation de l’adresse est faite par Cloudflare et isIP côté Next, pas par un parseur Lua inventé.

| Variable Coolify                                                       | Valeur cible                                                                             | Retour arrière                                                           |

Les valeurs OTP/VERIFY/TOKEN_REFRESH sont des débits par cinq minutes dans cette version, avec burst 30 ; ce ne sont pas des plafonds horaires stricts. Les compteurs sont en mémoire et distincts par groupe de routes ; signup, recover et resend utilisent le même réglage OTP mais chacun possède son compteur distinct (ainsi que /user). verify utilise la vérification. Le compteur TOKEN_REFRESH s’applique à /token, y compris à la connexion par mot de passe et au renouvellement : il n’est pas réservé au refresh. Un quota d’IP atteint doit produire un refus temporaire invitant à réessayer, pas un succès de récupération. GoTrue laisse passer une requête dont l’en-tête de limitation configuré est absent ou dont la première valeur est vide, en journalisant un avertissement : Envoy doit donc refuser toute requête Auth sans IP canonique fiable avant qu’elle atteigne GoTrue.

### IP partagées

Les réseaux mobiles, notamment marocains, et les écoles peuvent partager une IP publique entre de nombreux joueurs. Leurs requêtes alimentent le même compteur pour chaque route et atteignent donc les limites plus vite ; deux IP distinctes ne prouvent pas l’adéquation aux réseaux partagés. Les valeurs proposées sont un point de départ à mesurer, pas une validation de capacité. En cas de refus légitimes lors d’une connexion collective, le premier recours est de remonter le burst pour absorber la rafale, avant de modifier le débit soutenu, tout en gardant le captcha et la confiance IP. Dans GoTrue 2.196.0, ce burst est fixé à 30 dans le code : les variables RATE_LIMIT_* ne le relèvent pas. Une adaptation validée de GoTrue ou une version exposant ce réglage sera nécessaire ; aucune modification de GoTrue n’est incluse ici. Tester cette adaptation en environnement isolé avec plusieurs joueurs derrière une même IP, puis suivre les refus légitimes ; ne pas saturer la production.

Vérification avant activation : origine directe refusée même avec CF-Connecting-IP et en-têtes internes forgés ; API publique via Cloudflare disponible ; deux réseaux donnent deux IP différentes pour inscription/login/récupération via Server Actions ET API directe. Inspecter seulement les en-têtes canoniques/compteurs nécessaires par instrumentation temporaire contrôlée, sans cookies, mots de passe, clés ni preuve dans les logs ; supprimer cette instrumentation. Vérifier qu’une ancienne session reste utilisable, que les liens restent sur le domaine public et que REST utilise l’URL publique. Le test local auth-real-ip prouve l’inertie de l’URL seule et la nécessité de l’indicateur explicite, IPv4/IPv6, refus de preuves/IP invalides, conservation du corps et du cookie ; il ne prouve pas le réseau déployé.

Retour arrière : retirer d’abord GOTRUE_RATE_LIMIT_HEADER et redémarrer Auth, puis mettre AUTH_REAL_IP_ENABLED=false (ou le retirer) et redémarrer Next ; retirer ensuite SUPABASE_AUTH_INTERNAL_URL, restaurer les autres variables Auth une à une, enfin restaurer le filtre Envoy et les règles de preuve. Cet ordre évite que les appels publics de tous les joueurs partagent momentanément le compteur de l’IP du VPS. Conserver le blocage de l’origine Cloudflare si possible. Si le filtre reste actif, garder la preuve Traefik jusqu’à son retrait ; ne pas créer d’interruption par ordre inversé. Les règles Envoy, Traefik et le réseau ont leurs propres redéploiements ; le redémarrage Auth seul ne les applique pas. Ne jamais rétablir un limiteur qui accepte une IP fournie librement par un client.

## Vérifications bornées et conditions d’arrêt

Deux comptes jetables au maximum, deux boîtes contrôlées, idéalement deux réseaux. Aucun essai d’inscription en masse, aucune rafale, aucun épuisement de quota SMTP/Auth sans accord distinct. Les tests locaux utilisent des réponses simulées et aucune clé/session de production.

Avec accord pour les essais de production : une inscription/confirmation par compte, un renvoi prématuré et un renvoi après délai, une récupération, un réemploi de lien, un lien invalide, une redirection externe, et des essais négatifs limités côté API directe. Ne pas modifier les comptes existants. Prévoir un nettoyage des comptes jetables seulement après autorisation de cette opération.

Arrêter la bascule si livraison non démontrée, réseau de confiance incomplet, jeton captcha non traité dans un parcours ou quota OVH non confirmé. Vérifier disponibilité Auth après chaque étape et conserver les valeurs de retour arrière hors dépôt. Aucun accès SSH ni secret ne doit figurer dans les comptes rendus.

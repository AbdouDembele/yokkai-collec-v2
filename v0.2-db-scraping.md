# v0.2 — Base de données réelle & intégration du scraping

Objectif : sortir des placeholders, brancher une vraie DB alimentée par les données scrapées, et
ajouter des comptes utilisateurs réels. Le marché/enchères, le social (amis, échange, wishlist)
et les Karas restent hors scope — prévus en v0.3+.

## Stack DB

**Supabase** (Postgres + auth intégrée) — cohérent avec la recommandation faite en v0.1, le plus
rapide à brancher sur Next.js.

## Schéma de la table `cards` (pensé pour accueillir les données scrapées)

```
id              uuid (pk)
source_id       text        -- id d'origine côté source scrapée, pour dédoublonnage
nom             text
categorie       text        -- Anime/Manga, Sport, Cinéma, etc.
franchise       text        -- ex. le nom de l'anime/série source (titre EN)
franchise_romaji text (nullable) -- titre romaji, utile pour la recherche
rarete_base     enum(C,R,SR,SSR,LR)  -- rareté "naturelle" du perso, voir logique ci-dessous
image_url       text
favoris_count   integer (nullable) -- sert à l'attribution de la rareté, gardé pour référence
description     text (nullable)
source          text        -- d'où vient la donnée (site scrapé), utile pour debug/traçabilité
date_ajout      timestamp
```

Note : le Shiny n'est **pas** un champ du catalogue — c'est une variante tirée aléatoirement au
moment de l'ouverture d'un pack, stockée sur l'exemplaire possédé par le joueur (voir v0.3).

### Décisions prises sur le scraping (à partir du premier CSV fourni)

- **Format** : CSV, colonnes `id,personnage,anime_en,anime_romaji,image,favoris`
- **Nettoyage avant import** : retirer toute ligne dont `image` vaut l'image par défaut AniList
  (`https://s4.anilist.co/file/anilistcdn/character/large/default.jpg`) — ça veut dire que le
  perso n'a pas de vraie image, donc pas exploitable en carte
- **Attribution de la rareté** : basée sur `favoris`, mais en **seuils absolus fixes**, pas en
  percentile. Important car la base va grossir en continu (sport, musique, personnalités
  publiques...) : un système en percentile bougerait à chaque ajout et changerait la rareté de
  cartes déjà en circulation. Logique retenue :
  1. `favoris >= SEUIL_LR` → `LR` (rareté la plus haute directement "dropable")
  2. `favoris >= SEUIL_SSR` → `SSR`
  3. `favoris >= SEUIL_SR` → `SR`
  4. `favoris >= SEUIL_R` → `R`
  5. sinon → `C`
  - Les `SEUIL_*` sont des nombres fixes, calculés **une seule fois** en regardant la distribution
    du premier CSV (via quantiles, juste pour avoir un point de départ raisonnable), puis codés en
    dur. Un perso très favori scrapé plus tard tombera dans le bon seuil directement, sans
    recalcul global — voir `scripts/clean_and_assign_rarity.py`
  - Cette méthode marche pareil pour les futures catégories (sport, musique...) tant qu'on a un
    proxy de popularité équivalent à `favoris` pour chacune (à définir catégorie par catégorie)
- **Images** : re-upload sur Supabase Storage au moment de l'import (pas de dépendance à un lien
  externe qui peut mourir) — le script d'import télécharge chaque `image` du CSV et la ré-héberge

### Mapping CSV → table `cards`

| Colonne CSV    | Colonne DB         | Notes                                                                                                                   |
| -------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------- |
| `id`           | `source_id`        | gardé pour traçabilité/dédoublonnage, distinct du `id` uuid interne                                                     |
| `personnage`   | `nom`              |                                                                                                                         |
| `anime_en`     | `franchise`        | titre principal affiché                                                                                                 |
| `anime_romaji` | `franchise_romaji` | champ secondaire, utile pour la recherche plus tard                                                                     |
| `image`        | `image_url`        | après re-upload sur le storage                                                                                          |
| `favoris`      | `favoris_count`    | gardé en DB (pas juste utilisé puis jeté) — utile pour affiner le bucketing plus tard ou pour un futur tri "popularité" |
| — (fixe)       | `categorie`        | `"Anime/Manga"` pour tout ce batch                                                                                      |
| — (fixe)       | `source`           | nom du site/API scrapé                                                                                                  |
| — (calculé)    | `rarete_base`      | assignée par seuils fixes décrits ci-dessus                                                                             |
| — (auto)       | `date_ajout`       | timestamp de l'import                                                                                                   |

## Migration de l'architecture

Le module `lib/data/cards.ts` créé en v0.1 garde exactement la même interface
(`getAllCards()`, `getUserCollection()`, `openBooster()`...) — seule l'implémentation change
pour interroger Supabase au lieu du tableau en dur. Aucun composant ne doit changer.

## Comptes utilisateurs (version basique)

- Auth Supabase (email + mot de passe)
- Choix d'un pseudo à l'inscription
- La collection est désormais liée à un `user_id` réel au lieu de l'utilisateur unique en dur
- **Pas encore** : édition de profil (photo, bio, cartes mises en avant), amis, visite du profil
  d'autrui → reporté en v0.3

## Ce qui reste identique par rapport à la v0.1

- Regular Pack (10 cartes / 30 min), taux de drop C/R/SR/SSR
- Animation de reveal dos face → clic → tri par rareté croissante
- Page Collection (tri par rareté, filtres catégorie/rareté, date d'obtention)

## Ce qui est toujours HORS scope (reporté v0.3+)

- Decision Pack
- Karas, destruction de cartes
- Marché, enchères
- Système d'amis, échange
- Profil personnalisable
- Recherche, wishlist, notifications
- LR / Shiny LR et animations spéciales
